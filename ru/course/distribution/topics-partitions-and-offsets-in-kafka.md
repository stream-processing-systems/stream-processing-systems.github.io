# Топики, партиции и смещения в Kafka

> Как Kafka называет части разделённого журнала: топики, брокеры, записи с ключами и смещения, и почему смещение — адрес записи, а не идентичность события.

Source: https://stream-processing-systems.github.io/ru/course/distribution/topics-partitions-and-offsets-in-kafka/

Журнал (log) расхода нашего ИИ-ассистента
[разделён на партиции](https://stream-processing-systems.github.io/ru/course/distribution/splitting-a-log-into-partitions.md) (partitions), и
три обработчика (processor) делят их между собой. Сам журнал компания не
писала. Он работает на Apache Kafka, которая ещё и решает, какой обработчик
читает какую партицию, и следит, где каждый остановился.

Чтобы разобраться, как Kafka распределяет работу, сначала сопоставим её
термины с нашей моделью: как связаны топики, брокеры, записи и смещения.
Как выглядит журнал расхода в Kafka и как потребитель находит в нём свою
позицию?

## Топики и брокеры

Именованный журнал в Kafka называется **топиком** (topic). Наш называется
`usage`. Топик разделён на партиции точно как в нашей модели: каждая партиция
хранит записи в порядке дописывания, а записи с одним ключом (key) попадают в одну
партицию[^1]. У топика `usage` три партиции: 0, 1 и 2.

Kafka работает на нескольких серверах. Серверы, которые хранят партиции и
отдают их производителям (producers) и потребителям (consumers), называются
**брокерами** (brokers)[^1].
Партиции одного топика разнесены по разным брокерам, поэтому запись и чтение
тоже делятся между машинами. Ещё Kafka хранит копии каждой партиции на других
брокерах, чтобы отказ одного брокера не уносил его партиции с собой. Обычная
настройка — три копии[^1].

Шлюз и обработчики подключаются к брокерам. Шлюз — производитель,
который пишет в топик `usage`, а каждый обработчик — потребитель,
который из него читает.

## Запись: ключ, значение и метка времени

У записи Kafka есть ключ, значение, метка времени и необязательные заголовки с
дополнительными сведениями[^1]. У нашего шлюза ключ — ID аккаунта, а
значение — уже знакомая запись о расходе с ещё одним полем: `status` говорит,
успешно ли завершился запрос.

```json
{
  "usage_id": "u-103",
  "account_id": "acme",
  "tokens": 600,
  "status": "succeeded",
  "occurred_at": "2026-02-02T06:03:00Z"
}
```

Вот как шлюз её отправляет через Java-клиент Kafka:

```java
producer.send(new ProducerRecord<>("usage", "acme", usageJson));
```

Три аргумента — топик, ключ и значение. Партиция в коде не указана.
Производитель вычисляет её из хеша (hash) ключа `acme`, поэтому каждая запись
аккаунта попадает в одну и ту же партицию[^2].

Метка времени — не обязательно [время события](https://stream-processing-systems.github.io/ru/course/time/event-time-and-processing-time.md)
(event time). По умолчанию Kafka берёт время,
когда производитель создал запись; вместо него топик может использовать время,
когда брокер её дописал[^3]. Когда всё идёт гладко, оба близки ко времени
запроса, а когда запись задерживается, далеки от него. Поэтому в значении есть
`occurred_at`, и наш обработчик считает по времени события оттуда.

## Смещения

Позиция записи в партиции называется её **смещением** (offset). Kafka нумерует
каждую партицию с 0, и смещение однозначно указывает на запись внутри её
партиции[^4]. Поэтому позиции 1–5 партиции 0 из нашей модели становятся
смещениями 0–4:

| Смещение | Ключ | Запись | Токены |
| --- | --- | --- | --- |
| 0 | `acme` | `u-101` | 1 000 |
| 1 | `acme` | `u-102` | 400 |
| 2 | `delta` | `u-105` | 300 |
| 3 | `acme` | `u-102`, повторная отправка | 400 |
| 4 | `acme` | `u-103` | 600 |

Смещение имеет смысл только вместе со своей партицией. В партиции 1 тоже есть
смещение 2, и это другая запись. Полный адрес `u-103` — топик, партиция и
смещение: `usage`, 0, 4.

Прогресс чтения (reading progress) потребителя — тоже смещение: смещение
следующей записи, которую он получит. Потребитель на смещении 3 в партиции 0
получил записи со смещениями 0–2 и следующей получит копию `u-102`[^4]. Вот
обработчик, который читает топик и печатает адрес каждой записи:

```java
consumer.subscribe(List.of("usage"));
while (true) {
    for (ConsumerRecord<String, String> record : consumer.poll(Duration.ofSeconds(1))) {
        System.out.println(record.partition() + " " + record.offset() + " " + record.key());
    }
}
```

Каждый вызов `poll` возвращает очередную пачку записей с текущих позиций
потребителя и сдвигает позиции за возвращённые записи[^4]. У отстающего
потребителя в пачке окажутся записи, записанные давно. Из партиции ничего не удаляется: другой
потребитель может прочитать те же записи со своей позиции.

## Смещение — не ID события

У оригинала `u-102` и его копии разные смещения, 1 и 3, поэтому сравнение
смещений не поможет обнаружить повтор. Обработчик по-прежнему использует
`usage_id` для
[дедупликации](https://stream-processing-systems.github.io/ru/course/reliability/when-an-event-arrives-twice-or-never.md)
(deduplication).

Часть копий Kafka всё же убирает сама. Потерянное подтверждение
(acknowledgement) из истории нашего шлюза бывает и между производителем и
брокером: брокер сохраняет запись, его ответ теряется, и производитель
отправляет запись снова. На этот случай брокер даёт каждому производителю ID и
узнаёт повторную отправку по номеру последовательности, так что повтор не
добавляет в партицию вторую запись[^5]. Такой **идемпотентный производитель**
(idempotent producer) включён по умолчанию, если ему не мешают другие
настройки[^2].

Он защищает только от собственных повторов клиента для одной отправки. Если
приложение снова вызывает `send` для той же записи, Kafka видит новую запись,
и документация Java-клиента прямо говорит, что повторные отправки приложением
не покрываются[^6]. Так бывает, например, когда шлюз перезапускается уже после
того, как брокер сохранил `u-102`, и новый процесс шлюза отправляет запись
снова. Копия получит своё смещение, и только `usage_id` покажет, что это
копия. Поэтому обработчик сохраняет список учтённых ID, а идемпотентный
производитель снимает с него часть работы.

## Где живёт позиция потребителя

Позиция, которую сдвигает `poll`, живёт в памяти потребителя. В 11:00, когда
отказывает машина обработчика A, его позиция в партиции 0 пропадает вместе с
ней. Партиции 0 нужен новый читатель, а ему — позиция, с которой начать.
Кто-то должен заметить, что A остановился, выбрать, кто возьмёт партицию 0, и
дать ему смещение, которое соответствует восстановленному состоянию (state).
Kafka обнаруживает сбой, переназначает партицию и хранит смещения, которые
сохраняют потребители. Как новому читателю восстановить соответствующие им
итоги и списки учтённых ID?

## Что запомнить

- Топик — именованный журнал в Kafka, разделённый на партиции. Брокеры хранят
  партиции и держат их копии на других брокерах.
- У записи есть ключ, значение и метка времени. Производитель выбирает
  партицию по хешу ключа; метка времени — не обязательно время события.
- Смещение — позиция записи в одной партиции, нумерация с 0. Прогресс
  потребителя — смещение следующей записи, которую он прочитает.
- Смещение — адрес, а не идентичность события. Идемпотентный производитель
  убирает копии от собственных повторов клиента, а для копий, которые снова
  отправило приложение, по-прежнему нужен ID события.
